# kube-foundry v1.1.0

A contained operational-proof release for the existing local reference platform.

## Changes

- Verify exact Git revisions, immutable image digests, complete replica rollout, and API readiness during promotion and Git-revert rollback.
- Demonstrate Kyverno rejection of a missing CPU limit and successful corrected admission without disabling policy or persisting a test workload.
- Record timestamped, exclusive JSON evidence with cluster identity and explicit success/failure status.
- Verify a trusted archive checksum before creating a restore database; compare nonzero item/job counts and hashes before and after restoration, with application readiness checks on both sides.
- Refresh the web runtime's libexpat package after the release scan detected a high-severity finding. No scanner exceptions were added.

## Operator guidance

Acceptance passed on an isolated three-node cluster: historical Git promotion/revert, policy remediation, and recovery of all seven items and seven jobs on the final image set. The [publication pipeline](https://github.com/chriswayneh/kube-foundry/actions/runs/36665551929) passed validation, 20 unit tests, image scans, publication, and digest pinning. Full live verification passed after deployment of those digests.

The [operational walkthrough](https://github.com/chriswayneh/kube-foundry/blob/v1.1.0/docs/operational-proof.md) includes the acceptance record and reviewed evidence. Existing screenshots remain clearly dated v1.0 illustrations of the unchanged dashboards; they are not presented as fresh v1.1 captures.

Use `make install GITOPS_REVISION=v1.1.0` from the tagged checkout. Existing installations must retain their credentials and use `REUSE_SECRET=true` when the original environment file is unavailable. Platform/controller versions and application schemas are unchanged. Sample application and chart versions remain independent of this platform release.

## Boundaries

The promotion exercise uses one isolated kind cluster and an explicit operator-selected Git revision, not separate staging/production clusters. Historical image fixtures are only for disposable proof; a successful rollback does not establish current vulnerability clearance. Re-review images and compatibility before any real promotion or rollback.

Policy remediation is verified through server-side admission dry-run. Recovery restores into a separate database; the application continues using its original database. There is no production data cutover, Redis queue restore, automated off-host backup, RTO/RPO commitment, authentication expansion, or new controller.

See the [README](https://github.com/chriswayneh/kube-foundry/blob/v1.1.0/README.md) for setup and the full support boundary.
